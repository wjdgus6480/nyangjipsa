# 07. 회원 인증 구현 기록 (이메일 가입·인증, 카카오·구글 로그인, 비밀번호 재설정)

브랜치: `feature/auth` (origin/main `1413c00` 기준)

## 1. 한눈에 보기

| 기능 | 방식 |
|---|---|
| 이메일 회원가입 | 가입 → `pending`(인증 대기) + 인증 메일 → 링크 클릭 → `active` |
| 비밀번호 | Argon2id (m=19456 KiB, t=2, p=1), 8~128자·영문+숫자 |
| 로그인 유지 | 서버 세션 (`user_sessions`), 쿠키 `nj_session` = HttpOnly·SameSite=Lax·운영 Secure |
| 소셜 로그인 | 카카오·구글 OAuth 2.0 (state 검증, 이메일만으로 자동 연결 안 함) |
| 비밀번호 재설정 | 메일 링크(30분, 1회) → 새 비밀번호 → **모든 세션 폐기** |
| 관리자 | 공개 API 없음. `cargo run --bin create_admin -- grant <이메일>` 로만 지정 |
| 분석 | Amplitude HTTP API (키 없으면 꺼짐, 개인정보 제외) |

## 2. DB (`01_backend/migrations/0005_create_auth.sql`, 추가만)

기존 테이블(`hospitals`, `animal_businesses`, `region_fees`, `hospital_fees`)은 건드리지 않습니다.

| 테이블 | 핵심 |
|---|---|
| `users` | UUID PK, `email`(소문자 정규화, UNIQUE, NULL 가능), `nickname`(선택 1~20자), `password_hash`(NULL=소셜 전용), `role`(user/admin, 기본 user), `status`(pending/active/suspended/withdrawn), `email_verified_at`, 로그인 실패 횟수·잠금 |
| `user_auth_identities` | 로그인 수단(email/kakao/google). `UNIQUE(provider, provider_user_id)`, `UNIQUE(user_id, provider)` |
| `user_sessions` | 세션 토큰 **SHA-256 해시**만 저장, 만료·마지막 사용 시각 |
| `email_verifications` | 인증 대상 이메일 + 토큰 해시, 만료·사용 시각 (1회용) |
| `password_reset_tokens` | 토큰 해시, 만료·사용 시각 (1회용) |
| `user_consents` | 이용약관·개인정보 동의 + 정책 버전(`auth::POLICY_VERSION`) |

`roles`·`user_roles` 테이블은 만들지 않았습니다. 역할이 user/admin 둘뿐이라 `users.role` 컬럼(CHECK 제약)으로 충분하고, 늘어나면 그때 마이그레이션합니다.

## 3. API

모든 응답은 기존 규칙대로 snake_case JSON, 오류는 `{ "error": "…" }`.
상태를 바꾸는 요청(POST·PATCH·DELETE)은 `X-Requested-With: nyangjipsa` 헤더가 필요합니다(프론트 `services/api/client.ts` 가 자동으로 붙임).

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/api/auth/register` | 이메일 가입 (201, `email_sent`) |
| POST | `/api/auth/email/verify` | `{token}` 인증 → active |
| POST | `/api/auth/email/resend` | `{email}` 재발송 (1분 1회·1시간 5회, 응답은 가입 여부와 무관) |
| POST | `/api/auth/login` | `{email, password, remember}` → 세션 쿠키 |
| POST | `/api/auth/logout` | 세션 폐기 |
| GET | `/api/auth/me` | 내 정보 (비로그인 401) |
| POST | `/api/auth/password/forgot` | 재설정 메일 (응답은 가입 여부와 무관) |
| POST | `/api/auth/password/reset` | `{token, password, password_confirm}` |
| GET | `/api/auth/kakao`, `/api/auth/google` | 소셜 로그인 시작 (`?mode=link` = 로그인한 회원에 연결) |
| GET | `/api/auth/kakao/callback`, `/api/auth/google/callback` | 제공자 → 서버 → 프론트로 이동 |
| POST | `/api/auth/social/complete` | 소셜 신규 가입 마무리 (약관 동의·이메일) |
| PATCH | `/api/users/me` | 닉네임 수정 |
| PATCH | `/api/users/me/password` | 비밀번호 변경 (다른 기기 세션 폐기) |
| DELETE | `/api/users/me` | 회원 탈퇴 (비밀번호 확인) |
| GET | `/api/admin/users` | 관리자: 회원 목록 (일반 회원 403, 비로그인 401) |

기존 API(`/api/places/*`, `/api/hospitals/*`, `/api/chat`, `/api/route`)는 바꾸지 않았습니다.

- 헤더의 "로그인 / 회원가입" 은 `/login` 링크. 로그인하면 "닉네임님 · 로그아웃"
- 로그인 상태: `features/auth/AuthProvider.tsx` (Context). 비로그인 방문자에게는 `/api/auth/me` 를 호출하지 않도록 비밀이 아닌 힌트 쿠키 `nj_auth=1` 을 봅니다

## 5. 소셜 로그인 흐름과 계정 연결 정책

1. `/api/auth/{kakao|google}` → 무작위 state 를 HttpOnly 쿠키(`nj_oauth_state`, 10분)에 저장하고 제공자 동의 화면으로 이동
2. 콜백에서 쿠키 state 와 쿼리 state 비교(제공자까지 일치) → 서버가 code 로 토큰 교환(Client Secret 은 서버에서만) → 사용자 정보
3. 이미 연결된 소셜 계정 → 로그인. 처음이면:
   - 같은 이메일의 기존 계정이 있으면 **자동 연결하지 않고** `/login?social=email_exists` 안내 → 이메일로 로그인 후 내 정보에서 "연결하기"
   - 없으면 `pending` 계정 생성 → `/signup/social` 에서 약관 동의
     - 제공자가 **인증한** 이메일을 그대로 쓰면 즉시 active
     - 이메일 미제공·미인증이면 입력받은 이메일로 인증 메일 → 인증 후 active
4. 취소(`access_denied`)·실패·state 불일치는 로그인 화면에 안내만 하고 세션을 만들지 않음

## 6. 보안 설계 요약

- **관리자 권한**: 요청 구조체에 `role` 이 없고 `deny_unknown_fields` 라 `role`·`status` 를 보내면 400. 관리자 API 는 `AdminUser` 추출기가 매 요청 DB 에서 role 확인
- **세션**: 32바이트 OS 난수, DB 에는 SHA-256 만. 로그인마다 새 세션(이전 쿠키 세션 폐기 = 세션 고정 방지). 기본 24시간, "로그인 상태 유지"·소셜은 30일
- **CSRF**: SameSite=Lax + 상태 변경 요청에 사용자 정의 헤더 필수 + Origin 허용 목록. 운영 백엔드는 CORS 를 열지 않음
- **열거 방지**: 로그인 실패 문구 통일, 없는 계정도 더미 해시 검증(응답 시간 비슷), 재발송·비밀번호 찾기 응답 통일(재설정 메일은 백그라운드 발송)
- **무차별 대입**: IP·이메일별 분당 제한 + 5회 연속 실패 시 15분 잠금
- **SQL Injection**: 모든 값은 바인딩. 동적 SQL 은 코드 상수(테이블명·컬럼 목록)뿐이며 `sqlx::AssertSqlSafe` 로 표시
- **로그**: 비밀번호·토큰을 로그에 남기지 않음(설정 Debug 숨김, 메일 로그는 받는 주소 가림). 단 `MAIL_MODE=log` 는 개발용으로 **링크를 로그에 출력**하므로 운영에서는 서버가 시작을 거부
- **탈퇴**: 행은 남기고 이메일·닉네임·비밀번호를 비움, 로그인 수단·세션·토큰 삭제 → 같은 이메일·소셜로 재가입 가능

## 7. 환경변수와 외부 서비스 설정

저장소 루트 `.env` (예시: `.env.example`)

| 변수 | 설명 |
|---|---|
| `APP_BASE_URL` | 프론트 주소. 메일 링크·소셜 로그인 후 이동에 사용. **운영 필수(https)** |
| `COOKIE_SECURE` | 비우면 운영 true / 개발 false |
| `SESSION_HOURS`, `SESSION_REMEMBER_DAYS` | 세션 시간 (기본 24시간 / 30일) |
| `AUTH_ALLOWED_ORIGINS` | 추가 허용 출처(쉼표) |
| `MAIL_MODE` | `disabled`(기본) / `log`(개발 전용) / `smtp` |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_TLS` | SMTP 발송 (업체 무관) |
| `KAKAO_LOGIN_REST_API_KEY`, `KAKAO_LOGIN_CLIENT_SECRET`, `KAKAO_LOGIN_REDIRECT_URI` | 카카오 로그인 |
| `GOOGLE_LOGIN_CLIENT_ID`, `GOOGLE_LOGIN_CLIENT_SECRET`, `GOOGLE_LOGIN_REDIRECT_URI` | 구글 로그인 |

`02_frontend/.env.local`: `VITE_AMPLITUDE_API_KEY` (선택), `VITE_AMPLITUDE_SERVER_URL` (EU 프로젝트만)

### 카카오 (developers.kakao.com)
1. 앱 → [카카오 로그인] 활성화
2. Redirect URI 등록: 개발 `http://localhost:5173/api/auth/kakao/callback`, 운영 `https://<도메인>/api/auth/kakao/callback`
3. [동의항목] 닉네임, 카카오계정(이메일) 설정 (이메일은 비즈 앱 검수가 필요할 수 있음 → 미제공이어도 가입 가능하게 구현됨)
4. [보안] Client Secret 사용 시 `KAKAO_LOGIN_CLIENT_SECRET` 에 입력
5. REST API 키 → `KAKAO_LOGIN_REST_API_KEY` (길찾기와 같은 앱이면 같은 키)

### 구글 (Google Cloud 콘솔)
1. [OAuth 동의 화면] 구성 (범위: openid, email, profile)
2. [사용자 인증 정보] → OAuth 클라이언트 ID(웹 애플리케이션)
3. 승인된 리디렉션 URI: `http://localhost:5173/api/auth/google/callback`, 운영 주소
4. 클라이언트 ID·보안 비밀번호 → `GOOGLE_LOGIN_CLIENT_ID`, `GOOGLE_LOGIN_CLIENT_SECRET`

### 메일 (SMTP)
업체는 아직 정해지지 않았습니다. 어떤 SMTP 든 `MAIL_MODE=smtp` + `SMTP_*` 로 연결됩니다. 운영 전 발신 도메인의 SPF·DKIM·DMARC 설정이 필요합니다.

### 로컬 개발
```bash
# 루트 .env 에 추가 (개발): MAIL_MODE=log, APP_BASE_URL=http://localhost:5173
cd 01_backend && sqlx migrate run && cargo run   # 인증 메일 링크가 서버 로그에 출력됨
cd 02_frontend && npm run dev                     # http://localhost:5173
```

## 8. 관리자 지정 절차

1. 관리자로 쓸 사람이 일반 회원가입·이메일 인증 완료
2. DB 접근 권한이 있는 운영자가 서버에서 실행
   ```bash
   cd 01_backend
   cargo run --bin create_admin -- grant admin@example.com
   cargo run --bin create_admin -- revoke admin@example.com   # 해제
   ```
3. 권한이 바뀌면 그 회원의 세션은 모두 폐기 → 다시 로그인
